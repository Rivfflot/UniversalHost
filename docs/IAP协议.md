# IAP 在线升级 协议

## 用途与基本约定

- 将 BIN 文件拆分为若干帧，发送至设备进行在线升级。
- **在线升级完全由上位机主导**：握手、信息、数据、发送完成、擦除、写入、校验和升级后的重启均由上位机分别发送请求。设备处理当前请求，完成后等待下一条请求，不自动进入下一操作。进入 Bootloader 所需的重启属于握手请求的处理过程。
- 上位机采用停等方式：只有收到与当前请求匹配的成功 ACK，才发送下一帧或下一条命令。耗时操作执行期间没有成功 ACK，完成后才回复结果。
- 设备记住当前会话中已完成操作的结果，重复请求只重发该结果，不重复擦写或重启。设备启动后不主动广播：进入 IAP 时由上位机每隔 0.5 秒重发握手；升级后由上位机每隔 0.5 秒重发重启请求，等待 APP 就绪确认。
- **数据均为大端序**，多字节字段先发送高字节。
- 文中的字节、长度和偏移均指 8 位字节，不能直接用设备的 C 存储单元大小代替。
- `帧长度 = 数据区长度 + 7`，其中固定帧头为 5 字节，帧 CRC16 为 2 字节。
- 示例的从站地址均为 `0x00`。这是示例值，每个设备应是固定地址。
- 对于不能在当前运行环境执行 IAP 的设备，有效握手直接触发设备重启进入 Bootloader ，复位前不发送握手成功 ACK。上位机继续每隔 0.5 秒重发握手，重试总时长由上位机决定；Bootloader 启动且通信就绪后，收到握手才回复成功 ACK。阶段 `0x07` 用于升级完成后启动 APP，并确认 APP 已运行且通信就绪。
- 下文偏移从 `0` 开始，范围包含两端。`H` / `L` 分别表示高字节 / 低字节，`byte1` 是多字节字段的最高字节。
- 从站号错误时，设备静默丢弃，不应答。长度字段计算的帧长与接收到的实际帧长不符时，返回长度字段错误。判定顺序为：从站地址 → 长度 → CRC16 → 阶段/数据区。

## 通用帧格式

设 `L` 为数据区字节数。长度字段必须与实际数据区长度一致。

| 字节偏移 | 字节数 | 字段 | 说明 |
| --- | --- | --- | --- |
| `0` | 1 | 功能码 | `0x01` |
| `1` | 1 | 阶段 | 见阶段表 |
| `2` | 1 | 帧数据区长度 H | 数据区长度的高字节 |
| `3` | 1 | 帧数据区长度 L | 数据区长度的低字节 |
| `4` | 1 | 从站地址 | 设备固定地址，示例使用 `0x00` |
| `5 .. 4 + L` | `L` | 数据区 | 内容由阶段决定 |
| `5 + L` | 1 | `CRCH` | 帧 CRC16 高字节 |
| `6 + L` | 1 | `CRCL` | 帧 CRC16 低字节 |

| 阶段码 | 阶段名称 | 主要内容 |
| --- | --- | --- |
| `0x00` | IAP 握手 | 必要时触发重启进入 IAP；就绪后确认写入方式及一帧字节数 |
| `0x01` | IAP 信息 | 总帧数、ROM 长度、ROM CRC32 |
| `0x02` | 发送数据 | 当前帧号与 BIN 数据，设备返回收到的帧号 |
| `0x03` | 发送完成 | 检查数据接收是否完整及接收 CRC32，回复结果 |
| `0x04` | 开始擦除 | 设备完成擦除后回复结果 |
| `0x05` | 开始写入 | 整体写入设备完成烧录后回复结果 |
| `0x06` | 开始校验 | 完成目标回读 CRC32 校验后回复结果 |
| `0x07` | 升级后重启及 APP 就绪确认 | 校验成功后执行复位；APP 通信就绪后回复成功结果 |
| `0xFF` | 通用错误 | 接收帧校验错误、功能码错误 |

## CRC 校验

上位机和下位机使用相同的 CRC 算法及参数。实现见 [Crc.cs](../UniversalHost/Models/Crc.cs) 中的 `Crc.Crc16Modbus.Calculate` 和 `Crc.Crc32.Calculate`。

| 参数 | 帧 CRC16 | ROM CRC32 |
| --- | --- | --- |
| 算法 | CRC16-MODBUS | 使用反射多项式 `0xEDB88320` 的 CRC32 |
| 位宽 | 16 位 | 32 位 |
| 右移实现使用的反射多项式 | `0xA001` | `0xEDB88320` |
| 对应的非反射多项式 | `0x8005` | `0x04C11DB7` |
| 初始值 | `0xFFFF` | `0xFFFFFFFF` |
| 输入 / 输出反射（RefIn / RefOut） | `true / true` | `true / true` |
| 最终异或值（XorOut） | `0x0000` | `0xFFFFFFFF` |
| 计算范围 | 从功能码到数据区末尾，包含帧头，不包含末尾 CRC16 本身 | ROM `.bin` 文件的全部原始字节，不包含 IAP 帧头和帧 CRC16 |
| 发送顺序 | `CRCH CRCL`，高字节在前 | 4 字节大端序 |
| ASCII `123456789` 的校验结果 | `0x4B37` | `0xCBF43926` |

CRC16 的算法参数和结果字节顺序分别规定：本协议使用 CRC16-MODBUS 算法，CRC16 字段按大端序发送。

## ROM 分帧规则

握手确认中的“一帧字节数”由下位机指定，表示每个数据帧最多携带的 BIN 数据字节数，不包含帧号、帧头和 CRC16。

- 每帧字节数 `B` 的有效范围为 `[1, 1372]`。
- ROM 长度为 `.bin` 文件的原始字节数 `R`。
- 空 BIN 文件（`R = 0`）直接拒绝，上位机在建立通信和发送握手前停止升级并报错。
- 总帧数为 `ceil(R / B)`，向上取整。
- 帧号从 `0` 开始，最后一帧帧号为 `总帧数 - 1`。
- 最后一帧不足 `B` 字节时，只发送剩余部分，不补零或补齐。

对帧号 `i`：

```text
frame_count  = ceil(R / B)
rom_offset   = i * B
N            = min(B, R - rom_offset)
data_length  = N + 4             // BIN 数据 + 4 字节帧号
frame_length = N + 11            // 5 字节帧头 + 数据区 + 2 字节 CRC16
```

`i` 的有效范围为 `0 <= i < frame_count`。例如 `R = 3000`、`B = 1372` 时，总帧数为 3，帧号为 `0, 1, 2`，各帧 BIN 数据长度为 `1372, 1372, 256` 字节。

## 升级流程

### 必要时先进入 Bootloader

1. 上位机立即发送握手；未收到成功 ACK 时，每隔 0.5 秒重发同一握手包，直到收到成功 ACK 或达到上位机设定的握手重试总时长。
2. 当前程序能够直接执行 IAP 时，设备检查是否忙碌，不忙则回复握手 ACK，无需重启。
3. 当前程序必须先重启进入 Bootloader 时，设备收到有效握手并确认不忙后，直接重启进入 Bootloader ，复位前不发送握手成功 ACK。切换期间的重复握手直接忽略，不重复设置启动选择，也不再次触发重启。
4. Bootloader 实际启动且通信就绪后，收到上位机重发的握手，返回 ACK，并按当前环境返回写入方式 `bit0` 和每帧 BIN 字节数 `B`。等待信息帧时的重复握手只补发 ACK，不再次重启。
5. 上位机收到成功 ACK 后，继续后续流程，无需额外握手。

本流程没有设备固定的握手重试次数；上位机设定的握手重试总时长应覆盖复位、IAP 程序启动及通信初始化。

若设备实现了接收超时，超时后 Bootloader 仍保持可通信。若还没有写入 flash，重新计数启动超时跳转 APP。

不需要进入 Bootloader 的设备直接回复握手 ACK。

### 逐帧写入设备（bit0 = 1）

1. 上位机按上述握手流程建立会话，收到握手 ACK。
2. 上位机发送信息帧，设备检查元数据及容量并 ACK；此时不擦除。
3. 上位机发送开始擦除，设备擦除，完成后 ACK。
4. 上位机逐帧发送数据；设备处理当前帧完成后回复对应帧号 ACK，上位机再发送下一帧。
5. 上位机发送发送完成，设备检查帧数、接收长度及接收 CRC32，完成后 ACK。
6. 上位机发送开始校验，设备写完可能尚未落盘的尾部编程单元、回读目标并校验 CRC32，完成后 ACK。
7. 上位机每隔 0.5 秒发送阶段 `0x07` 重启请求。设备处于目标校验成功、等待重启状态时，收到请求后提交启动、关闭通信并复位，不在复位前发送成功 ACK。
8. APP 启动且通信就绪后，上位机重发的阶段 `0x07` 请求收到成功 ACK。该 ACK 只表示 APP 已运行且通信就绪；上位机结合本次升级前序步骤的结果判断升级是否完成。

逐帧模式没有单独的“开始写入”步骤，数据帧处理时完成写入或复制到编程单元缓存。

### 整体写入设备（bit0 = 0）

1. 上位机按上述握手流程建立会话，收到握手 ACK。
2. 上位机发送信息帧，设备检查元数据及容量并 ACK。
3. 上位机逐帧发送数据；设备暂存当前帧并回复对应帧号 ACK，上位机再发送下一帧。
4. 上位机发送发送完成，设备检查帧数、接收长度及接收 CRC32，完成后 ACK；此时不擦除目标。
5. 上位机发送开始擦除，设备擦除，完成后 ACK。
6. 上位机发送开始写入，设备把暂存 BIN 烧录到目标，完成后 ACK。
7. 上位机发送开始校验，设备回读目标并校验 CRC32，完成后 ACK。
8. 上位机每隔 0.5 秒发送阶段 `0x07` 重启请求。设备处于目标校验成功、等待重启状态时，收到请求后提交启动、关闭通信并复位，不在复位前发送成功 ACK。
9. APP 启动且通信就绪后，上位机重发的阶段 `0x07` 请求收到成功 ACK。该 ACK 只表示 APP 已运行且通信就绪；上位机结合本次升级前序步骤的结果判断升级是否完成。

### Bootloader 启动监听

设备由有效握手触发进入 Bootloader 后，等待上位机每隔 0.5 秒重发握手。设备等待时间应大于 0.5 秒 + 初始化时间，避免跳转回 APP，导致握手与重启循环。握手成功后等待信息帧，后续流程继续由上位机决定。

若写完 ROM 后重启时设备的实现是复位并重新进入 Bootloader，Bootloader 在没有前序流程的情况下收到阶段 `0x07` 请求时必须静默忽略：不应答、不再复位，并继续执行自身的启动超时，随后跳转到 APP。上位机按 0.5 秒间隔继续重发请求；APP 启动且通信就绪后返回 APP 就绪 ACK。

仅在普通上电、尚未因握手进入 Bootloader、也未开始会话时，可按设备规定的初始监听时限跳转到有效 APP。

初始监听时限不用于已经开始接收或擦写、随后中止的会话。此时保持 Bootloader 可通信状态，等待上位机重新开始完整升级。

## 超时、重试与异常恢复

### 上位机等待规则

| 请求 | 重发间隔 | 等待上限 |
| --- | --- | --- |
| 握手（含必要的重启进入 Bootloader） | 固定 0.5 秒，重发同一握手包 | 握手重试总时长由上位机决定，须覆盖复位、IAP 启动及通信初始化 |
| 信息帧、数据帧、发送完成 | 上位机配置的通信接收超时 | 上位机配置的重试次数，不设置独立阶段总超时 |
| 开始擦除、开始写入、开始校验 | 固定 0.5 秒，重发同一请求 | 各自的操作总超时，必须覆盖最坏操作耗时及通信延时 |
| 升级后重启及 APP 就绪确认 | 固定 0.5 秒，重发相同请求 | 重启总超时，必须覆盖复位、APP 启动及通信初始化 |

- 握手首次立即发送，之后每隔 0.5 秒重发，直到成功或握手重试总时长耗尽；不能因为设备正在复位而提前套用较短的数据帧重试次数停止握手。
- 本上位机握手重试总时长默认 5 秒，可按设备启动及初始化耗时配置。
- 对握手之外按次数重试的请求，配置重试次数为 `K` 时，除首次发送外最多再发送 `K` 次。
- 耗时操作等待期间，上位机不能套用较短的数据帧重试上限提前判定失败；在该操作总超时内每隔 0.5 秒重发请求即可。
- 上位机收到与当前请求匹配的成功 ACK 后立即推进，正常数据帧间隔可在 1 ms 量级。收到其他阶段或其他帧号的 ACK，不能推进当前流程。阶段 `0x07` 的成功 ACK 仅确认 APP 运行且通信就绪，上位机还须确认本次升级的前序步骤均已成功。
- 达到当前请求的等待上限后，上位机报故障并停止该流程；是否重新开始由上位机决定。

### 设备重复请求规则

- **当前耗时操作正在执行**：同一请求的重发直接忽略，不重做操作，也不立即 ACK。操作完成时回复一次最终结果，不按执行期间收到的重复请求数量逐条回复。
- **操作已经完成**：保存成功或失败结果；之后收到相同请求立即重发保存的结果。即使已经进入后续阶段，也不得再次执行旧操作。例如写入期间收到延迟的擦除请求，只补发擦除结果。
- 数据帧只按顺序处理一次；成功接收的旧帧重复到达时只补发对应帧号 ACK，不重复写入、累计帧数或计算 CRC32。
- 设备只在响应上位机请求时发送操作结果。
- 当前阶段不允许的请求返回状态错误，不提前执行后续操作；帧格式或参数错误也不能触发硬件动作。例外：Bootloader 启动后没有前序升级会话上下文时收到阶段 `0x07` 重启帧，按阶段 `0x07` 状态表静默忽略，不返回状态错误。

### 重新开始与错误处理

- **有效握手帧**：在等待信息帧时，视为重复握手，只补发握手 ACK。握手已经触发重启进入 IAP、正在关闭通信或复位时，重复握手直接忽略，不提前 ACK、不重新触发切换。其他升级阶段收到有效握手，取消旧会话后续动作、释放临时资源，清空镜像信息、帧号、接收长度、CRC 和操作结果，再检查忙碌并建立新会话；不必等待旧会话超时。
- 硬件步骤不可立即中断时，在当前步骤结束后停止旧会话后续步骤并处理新握手，不继续旧流程。**无论复位由进入 IAP 的握手还是升级后的重启命令触发，已经开始关闭通信或复位时，握手均不能取消该复位，也不回复握手成功 ACK。**
- 阶段 `0x07` 不使用启动确认缓存；其行为由设备当前运行环境和升级会话状态决定。
- 单帧 CRC16 或格式错误时，返回通用错误，保留已接受的升级进度，允许重发当前帧。
- 帧数、接收长度、ROM CRC32 或存储操作错误时，保存失败结果并停止旧会话的后续操作，不自动擦写或重启；重复请求只重发失败结果，新的有效握手才能重新开始。
- 旧会话已部分擦写时，无需回滚或自行恢复旧镜像，设备保持 IAP 可通信状态，依赖上位机发起新的完整升级。新会话数据接收、写入和目标校验都成功后，仍须等待上位机发出重启命令。
- 设备可设置接收空闲超时，默认 10 秒。等待上位机下一条请求时到期可取消会话并释放资源；不能在当前耗时操作执行期间用该空闲超时中止操作。操作完成后重新起算空闲时间，也不能把超时后的空闲状态当作“刚启动”状态。

上位机须按从站地址、阶段和当前流程状态匹配响应。传输层应隔离非目标设备或发送端，并按所用链路规则解析帧边界和接收数据。阶段 `0x07` 不含序号，其成功 ACK 只表示 APP 已运行且通信就绪，不标识具体固件版本。

## 阶段 0x00：IAP 握手

### PC 发送：握手信息

| 功能码 | 阶段 | 长度 H | 长度 L | 从站地址 | 数据区 | 帧 CRC |
| --- | --- | --- | --- | --- | --- | --- |
| `0x01` | `0x00` | `0x00` | `0x02` | `0x00` | `0xAA 0xAA` | `CRCH CRCL` |

数据区为 2 字节，总帧长度为 9 字节。

设备必须先确认帧格式、CRC16、从站地址及握手数据正确，再检查是否忙碌。当前程序需要重启进入 IAP 时，合法握手直接触发环境切换，不在复位前发送成功 ACK；就绪后的 IAP 程序接收到重发的握手才返回下面的确认信息。

### 设备返回：确认信息

| 字节偏移 | 字段 | 内容 |
| --- | --- | --- |
| `0` | 功能码 | `0x01` |
| `1` | 阶段 | `0x00` |
| `2` | 帧数据区长度 H | `0x00` |
| `3` | 帧数据区长度 L | `0x04` |
| `4` | 从站地址 | `0x00` |
| `5` | 确认值 | `0x00` |
| `6` | 标志字节 | `bit0` 表示写入方式，其余位保留 |
| `7` | 一帧字节数 H | 由设备返回 |
| `8` | 一帧字节数 L | 由设备返回 |
| `9` | 帧 CRC 高字节 | `CRCH` |
| `10` | 帧 CRC 低字节 | `CRCL` |

| 标志位 | 值为 `0` | 值为 `1` |
| --- | --- | --- |
| `bit0` | 整体写入 | 逐帧写入 |

标志字节中除 `bit0` 外的位当前保留；发送端置 `0`，接收端忽略。两个“一帧字节数”字节按大端序组成一个 16 位值。

数据区为 4 字节，长度字段为 `0x0004`，总帧长度为 11 字节。一帧字节数必须满足 `[1, 1372]`。设备返回的数据无效时上位机停止流程并显示错误。

需要重启进入 Bootloader 的设备在有效握手后直接切换运行环境，不在切换前返回握手成功 ACK。重启后的 Bootloader 程序收到上位机重发的握手后，再返回写入方式 `bit0` 和 `B`。是否需要切换由下位机平台启动流程处理，不通过握手标志通知上位机。

### 设备返回：设备忙

| 功能码 | 阶段 | 长度 H | 长度 L | 从站地址 | 数据区 | 帧 CRC |
| --- | --- | --- | --- | --- | --- | --- |

## 阶段 0x02：发送数据

### PC 发送：当前帧

设 `N` 为本帧 BIN 数据字节数。

| 字节偏移 | 字节数 | 字段 | 内容 / 说明 |
| --- | --- | --- | --- |
| `0` | 1 | 功能码 | `0x01` |
| `1` | 1 | 阶段 | `0x02` |
| `2 .. 3` | 2 | 帧数据区长度 | `N + 4`，大端序 |
| `4` | 1 | 从站地址 | `0x00` |
| `5 .. 8` | 4 | 当前帧号 | 大端序 |
| `9 .. 8 + N` | `N` | BIN 数据 | 当前帧的 `N` 字节 BIN 数据 |
| `9 + N` | 1 | 帧 CRC 高字节 | `CRCH` |
| `10 + N` | 1 | 帧 CRC 低字节 | `CRCL` |

总帧长度为 `(N + 4) + 7 = N + 11` 字节。

帧号从 `0` 开始，最后一帧不补齐。新帧必须是当前期待的下一帧，BIN 数据长度必须满足分帧规则；成功接收时应答`0x00`；帧号跳跃、越界时应答 `0x01`。重发时必须保持原帧号、长度及 BIN 内容不变；已接受的旧帧只补发 ACK。

逐帧模式只有在擦除成功后才接受数据帧；整体模式在信息 ACK 后即可接受。逐帧模式的新帧应写入目标或复制到编程单元缓存，整体模式的新帧复制到整包暂存区。当前帧处理成功后才回复对应帧号 ACK。

若 Flash 的编程单元大于单帧数据量，可以在缓存当前帧后先 ACK；不能等待后续帧凑满编程单元才回复本帧，否则停等传输无法继续。所有缓存内容必须在校验 ACK 前写入目标。

逐帧模式下写入错误时返回帧写入错误，上位机中止流程，发送新的握手重新开始 IAP 流程。暂存错误结果，重复到达同一帧号时重发相同 ACK。新的有效握手才能重新开始。

| 功能码 | 阶段 | 长度 H | 长度 L | 从站地址 | 数据区 | 帧 CRC |

成功 ACK 只表示完整 BIN 已被设备接受且接收 CRC32 正确，不代表目标区已经校验成功。设备随后等待上位机命令：逐帧模式等待开始校验，整体模式等待开始擦除。发送完成本身不会触发擦除、整体烧录、目标校验或重启。

## 操作请求与公共结果格式

阶段`0x03`、`0x04`、`0x05`、`0x06` 的上位机请求均使用两字节数据区 `0x00 0x00`，由阶段码区分操作；设备回复相同阶段码和两字节结果。请求、回复总帧长度均为 9 字节。

请求的数据区必须保持为 `0x00 0x00`；其他值返回参数错误 `0x0104`，不能触发操作。

| 字节偏移 | 字段 | 设备回复的内容 |
| --- | --- | --- |
| `0` | 功能码 | `0x01` |
| `1` | 阶段 | 对应请求的阶段码 |
| `2 .. 3` | 数据区长度 | `0x0002` |
| `4` | 从站地址 | 设备固定地址，示例 `0x00` |
| `5 .. 6` | 结果 | 下表中的两字节大端值 |
| `7 .. 8` | 帧 CRC16 | `CRCH CRCL` |

| 结果值 | 含义 |
| --- | --- |
| `0x00FF` | 请求处理成功；耗时操作已完成 |
| `0x0100` | 帧数或接收长度错误 |
| `0x0101` | BIN 接收 CRC32 或目标回读 CRC32 错误 |
| `0x0102` | 存储、擦除、写入、回读或启动目标提交失败 |
| `0x0103` | 当前状态不允许该请求 |
| `0x0104` | 请求参数无效 |

阶段 `0x07` 也使用上述两字节结果格式，详见该阶段。

结果 `0x0100`、`0x0101`、`0x0102` 终止当前升级后续操作，重复请求重发失败结果。状态或参数错误只拒绝该请求，不执行硬件操作，也不清空已有有效进度。

## 阶段 0x04：开始擦除

### PC 发送

| 功能码 | 阶段 | 长度 H | 长度 L | 从站地址 | 数据区 | 帧 CRC |
| --- | --- | --- | --- | --- | --- | --- |
| `0x01` | `0x04` | `0x00` | `0x02` | `0x00` | `0x00 0x00` | `CRCH CRCL` |

- 逐帧模式：只在有效信息帧已经接受、尚未开始接收数据时执行。
- 整体模式：只在发送完成检查成功后执行；不得在完整 BIN 尚未接收和校验时擦除目标。
- 设备收到合法请求后开始擦除；执行期间同一请求的重发直接忽略。
- 擦除结束后以阶段 `0x04` 回复结果 `0x00FF`，失败回复 `0x0102`。之后的重复擦除请求只重发保存的结果，不再次擦除。
- 擦除成功后，逐帧模式等待数据帧，整体模式等待开始写入请求，不自动烧录。

## 阶段 0x05：开始写入

### PC 发送

| 功能码 | 阶段 | 长度 H | 长度 L | 从站地址 | 数据区 | 帧 CRC |
| --- | --- | --- | --- | --- | --- | --- |
| `0x01` | `0x05` | `0x00` | `0x02` | `0x00` | `0x00 0x00` | `CRCH CRCL` |

只适用于整体写入模式，且必须先完成发送完成检查和擦除。设备把暂存 BIN 烧录到目标，执行期间忽略重复请求，完成后以阶段 `0x05` 回复 `0x00FF`，失败回复 `0x0102`。

写入成功后等待开始校验，不自行执行校验。重复写入请求只重发已保存结果。逐帧模式收到该请求返回状态错误 `0x0103`。

## 阶段 0x06：开始校验

### PC 发送

| 功能码 | 阶段 | 长度 H | 长度 L | 从站地址 | 数据区 | 帧 CRC |
| --- | --- | --- | --- | --- | --- | --- |
| `0x01` | `0x06` | `0x00` | `0x02` | `0x00` | `0x00 0x00` | `CRCH CRCL` |

- 逐帧模式：发送完成检查成功后才可执行；校验前必须把尚未写入的尾部编程单元刷写到目标。
- 整体模式：开始写入成功后才可执行。
- 从目标存储区回读原始 BIN 长度的字节，计算 CRC32，与信息帧中的 ROM CRC32 比较。不能只再次校验接收缓存。
- 执行期间忽略重复请求，结束后以阶段 `0x06` 回复结果：成功 `0x00FF`、CRC32 不符 `0x0101`、尾部写入或回读失败 `0x0102`。
- 成功后等待上位机重启请求，不自行关闭通信或复位。重复校验请求只重发保存结果。

## 阶段 0x07：升级后重启及 APP 就绪确认

阶段 `0x07` 请求的数据区固定为 `0x00 0x00`，不包含目标模式或请求序号。处于完整升级且目标校验成功后的等待重启状态时，该请求触发设备提交启动、关闭通信并复位。APP 启动且通信就绪后，上位机继续发送该请求以确认 APP 就绪。

成功 ACK 只表示**设备当前运行在 APP 且通信就绪**，不保证当前 APP 一定是本次刚写入的固件。上位机必须结合本次升级流程中信息、数据接收、擦除、写入（如适用）和目标校验等步骤的成功结果判断升级是否完成。设备在目标校验成功、等待重启状态收到请求后，必须先执行启动提交、关闭通信并复位，不得在复位前发送成功 ACK。上位机持续每隔 0.5 秒发送同一请求，既重试重启命令，也探测 APP 是否就绪。

### PC 发送：重启请求

| 字节偏移 | 字节数 | 字段 | 内容 |
| --- | --- | --- | --- |
| `0` | 1 | 功能码 | `0x01` |
| `1` | 1 | 阶段 | `0x07` |
| `2 .. 3` | 2 | 数据区长度 | `0x0002` |
| `4` | 1 | 从站地址 | 示例 `0x00` |
| `5 .. 6` | 2 | 请求参数 | 固定为 `0x00 0x00` |
| `7 .. 8` | 2 | 帧 CRC16 | `CRCH CRCL` |

数据区为 2 字节，总帧长度为 9 字节。与阶段 `0x04`、`0x05`、`0x06` 的操作请求一致，数据区固定为 `0x00 0x00`；其他值为参数错误，不得触发复位。

### 设备返回：APP 就绪结果

| 字节偏移 | 字节数 | 字段 | 内容 |
| --- | --- | --- | --- |
| `0` | 1 | 功能码 | `0x01` |
| `1` | 1 | 阶段 | `0x07` |
| `2 .. 3` | 2 | 数据区长度 | `0x0002` |
| `4` | 1 | 从站地址 | 示例 `0x00` |

数据区为 2 字节，总帧长度为 9 字节。上位机收到从站、阶段匹配且结果为 `0x00FF` 的响应后，可确认设备当前运行在 APP 且通信就绪；该响应不单独证明本次升级固件已生效。没有前序升级会话上下文的 Bootloader 静默忽略此请求，上位机继续重试，直到 APP 返回成功 ACK 或重启总超时到期。参数不是`0x0000`时按公共错误表返回`0x0104`。

### 设备处理规则

| 当前状态 | 收到有效重启请求后的动作 |
| --- | --- |
| 目标校验成功，等待升级完成后的重启 | 提交有效镜像及 APP 启动选择，关闭通信并复位，复位前不发成功 ACK |
| 已接受重启，正在关闭通信或复位 | 忽略重复请求，不重复提交启动动作、不提前 ACK；不接受握手取消重启 |
| Bootloader 启动后没有前序升级会话上下文 | 静默忽略，不应答、不复位，继续执行 Bootloader 自身的启动超时及跳转 APP |
| APP 正在运行、通信已就绪，且本次启动后没有前序升级会话 | 回复 `0x00FF`，表示 APP 已运行；不复位，也不判断 APP 是否为本次刚写入的固件 |
| 其他状态，包括仅完成握手、传输、擦写、校验及中止或取消的会话 | 返回 `0x0103`，不复位，也不返回成功 |

普通非 IAP 重启与 IAP 重启后的 APP 启动不做区分。阶段 `0x07` 成功 ACK 只说明 APP 已运行且通信就绪；上位机需结合本次已成功完成的升级流程判断是否显示“升级完成”。

一旦已开始执行实际复位，优先按“正在关闭通信或复位”处理，不再补发任何启动成功 ACK。设置 APP 启动选择或提交镜像失败时可在复位前返回 `0x0102`，并保持通信，不应执行复位。上位机收到 0x0102 后停止本流程并报故障，是否重试由上位机决定；若重试，应重新握手开始完整升级，避免设备处于半提交状态。

### 无前序会话时的确认

- 没有前序升级会话的 Bootloader 遇到阶段 `0x07` 请求时静默忽略，由自身启动超时机制继续跳转 APP。静默忽略仅针对数据区为 `0x0000` 的有效请求。
- APP 已启动且通信就绪、并且本次启动后没有前序升级会话时，收到阶段 `0x07` 请求回复 `0x00FF`；不建立持久的启动确认记录，也不写入 Flash。
- 接收空闲超时或取消升级会话后，设备不能把该会话误当成“没有前序升级会话”，只清除资源不清除标志位；此时阶段 `0x07` 请求返回 `0x0103`，避免上位机误判中止的升级已完成。
- 设备成功回复握手 ACK 时置位；实际复位后清除。根据该标志判断是否“没有前序升级会话”。

### 传输层要求

UDP 与串口 COBS 封装、连续传输分帧、物理链路限制、串口 XCP / IAP 互斥及上位机时序要求见 [传输层约定.md](传输层约定.md)。串口对完整 IAP 帧（含 CRC16）编码并追加 `0x00` 分隔符，UDP 保持原帧格式。

上位机通过所用传输链路每隔 0.5 秒重发当前等待阶段的请求：进入 IAP 时发握手，升级后发阶段 `0x07` 请求。传输适配层负责收发完整协议帧、隔离非目标设备或发送端，并按链路规则处理帧边界。上位机的握手重试总时长或重启总超时应覆盖设备复位、启动及通信初始化过程。

## 阶段 0xFF：通用错误

以下每一项都是设备返回帧。固定字段为：功能码 `0x01`、阶段 `0xFF`、长度 H `0x00`、长度 L `0x02`、从站地址 `0x00`、末尾 `CRCH CRCL`。总帧长度为 9 字节。

| 错误 | 数据区字节 0（偏移 5） | 数据区字节 1（偏移 6） |
| --- | --- | --- |
| 接收帧校验错误 | `0xFF` | `0x00` |
| 功能码错误 | `0xFE` | `0x00` |
| 长度字段错误 | `0xFD` | `0x00` |
| 阶段码错误 | `0xFC` | `0x00` |
