# 文件传输协议

本协议用于 UniversalHost 与资源受限的设备之间传输小文件。上位机（PC）发起每个请求，设备每收到一次请求最多应答一次。设备同一时刻只允许一个文件会话，PC 同一时刻只等待一个请求的结果（停等）。

| 传输方向 | 正常命令顺序 | 完成成功应答的含义 |
| --- | --- | --- |
| 设备 → PC | 开始 → 读取数据（重复至读完）→ 完成 | 设备已核对快照的长度和 CRC32 并释放快照，PC 可将临时文件发布为最终文件 |
| PC → 设备 | 开始 → 写入数据（重复至写完）→ 完成 | 设备已核对暂存文件的长度和 CRC32，并成功提交到目标 |

按字节实现请查[原始帧](#原始帧)和[命令布局](#命令布局)。处理丢帧请查[重试与会话结束](#重试与会话结束)。联调可直接使用[完整报文示例](#完整报文示例)。

## 链路与通道

| 链路 | 帧边界与分流 |
| --- | --- |
| UDP | 文件服务与 IAP 共用配置的本地和远端 IP、端口。一个接收入口校验远端 IP 和端口，再按数据报首字节分流。`0x02` 表示文件传输，一个数据报恰好一帧。`0x01` 交给 IAP，沿用其多帧解析规则。XCP 使用独立 UDP 端口。 |
| 串口 | 每帧发送 `COBS(含 CRC16 的完整原始帧) + 0x00`。接收方按分隔符拆帧、解码，再读功能码。串口会话首次发送前另发一个同步分隔符 `0x00`，接收方忽略空帧。串口由一个业务入口仲裁收发。 |
| 两线半双工 RS-485 | PC 发请求后让出总线。双方均须等末尾分隔符实际发完再换向，设备按链路换向裕量应答。耗时操作也由 PC 轮询。 |

设备侧 IAP 与文件传输互斥。IAP 活动时，新的文件开始请求返回文件状态 `0x04`。文件会话活动时，合法 IAP 握手使用 IAP 已定义的设备忙应答。串口封装和 IAP 握手分别见[传输层约定](传输层约定.md)和[IAP 协议](IAP协议.md)。

`Channel` 选择固件提供的文件源或写入目标。通道及支持的方向由固件定义。文件内容逐字节透传。

## 原始帧

所有数字字段均为无符号整数，多字节字段使用**大端序**。长度和偏移以 8 位字节计。下表使用**原始帧绝对偏移**，从 0 起算。`L` 是从 `Channel` 到命令体末尾的数据区长度，原始帧总长为 `L + 7`。

| 原始帧偏移 | 类型 / 长度 | 字段 | 线上含义 |
| ---: | --- | --- | --- |
| 0 | u8 | Function | 固定为 `0x02` |
| 1 | u8 | Command | 请求和应答使用同一命令码 |
| 2 | u16 | L | 数据区公共字段 11 字节，加命令体长度 |
| 4 | u8 | Station | 设备的 IAP 从站地址 |
| 5 | u16 | Channel | 文件通道，应答回显 |
| 7 | u32 | RequestId | PC 为每个新请求分配，应答回显 |
| 11 | u32 | SessionId | 开始请求时忽略，可填 0。开始成功时由设备分配，**0 也是有效编号**。开始未成功时 PC 忽略此字段。其他请求携带当前会话编号，应答回显。 |
| 15 | u8 | Flag / Status | 请求固定为 `0xFF`，应答填状态码 |
| 16 | `L - 11` 字节 | 命令体 | 由命令码、请求或应答、应答状态三者确定 |
| `5 + L` | u16 | FrameCrc16 | 从偏移 0 起计算前 `5 + L` 字节，结果高字节先发 |

`RequestId` 和 `SessionId` 各自按 u32 递增，从 `0xFFFFFFFF` 回绕到 0。设备启动时没有活动会话。本协议用于串口和局域网，按在途报文延迟远短于重启时间设计。分配方重启后可从固定初值重新编号，无需跨重启隔离重复编号。

### 校验和

| 字段 | 输入字节与参数 | ASCII `123456789` 的结果（线上顺序） |
| --- | --- | --- |
| FrameCrc16 | CRC16-MODBUS，覆盖原始帧头和数据区。初值 `0xFFFF`，右移多项式 `0xA001`，最终异或 `0x0000` | `4B 37` |
| FileCrc32 | 覆盖从偏移 0 到文件末尾的全部原始文件字节，按文件顺序每字节计入一次。初值 `0xFFFFFFFF`，右移多项式 `0xEDB88320`，最终异或 `0xFFFFFFFF` | `CB F4 39 26` |

两种算法的 RefIn / RefOut 均为 true。分块累计文件 CRC32 时，块间保留计算状态，文件结束才做最终异或。COBS 块码和串口分隔符均在帧校验范围之外。算法与[现有 CRC 实现](../UniversalHost/Models/Communication/Crc.cs)一致。

## 命令布局

下表从原始帧偏移 **16** 开始，字段按发送顺序排列，紧密相接。括号内的 `L` **包含 11 字节公共字段**。`N` 表示本块的文件字节数，`Data[N]` 是恰好 N 个原始字节。读取应答和写入请求的 `N = L - 15`。

| Command | PC 请求的命令体 | 设备成功应答的命令体（Status = 0x00） |
| --- | --- | --- |
| `0x00` 开始 | `Direction:u8 TotalLength:u32 MaxBlockLen:u16`（L = 18） | `TotalLength:u32 BlockLenLimit:u16`（L = 17） |
| `0x01` 读取数据 | `Offset:u32 Length:u16`（L = 17） | `Offset:u32 Data[N]`（L = 15 + N，N 等于请求的 Length） |
| `0x02` 写入数据 | `Offset:u32 Data[N]`（L = 15 + N） | `NextOffset:u32`（L = 15，值等于请求的 Offset + N） |
| `0x03` 完成 | `TotalLength:u32 FileCrc32:u32`（L = 19） | 空（L = 11） |
| `0x04` 取消 | 空（L = 11） | 空（L = 11），表示已取消 |

**非成功应答**仅在读写命令返回 `0x07` 时携带 `NextOffset:u32`（L = 15）。其余已定义的非成功应答均为空命令体（L = 11），包括请求仍在处理（`0x0A`）和提交中无法取消（`0x0B`）。PC 须先读状态，再决定按哪种布局取字段。

### 开始与块长协商

| Direction | 请求中的 TotalLength | 设备接受请求的条件和动作 |
| --- | --- | --- |
| `0` 设备 → PC | 填 0 | 检查通道有完整、非空的快照，固定读源后返回实际总长度。录波仍在采集时返回 `0x01`。会话内同一文件偏移始终对应相同字节。 |
| `1` PC → 设备 | 填待传文件长度，必须大于 0 | 检查通道写权限、设备运行状态和容量，备好暂存区后回显总长度。运行状态暂不允许写入返回 `0x02`，空间不足返回 `0x03`。 |

文件长度可表示的范围为 1 至 `0xFFFFFFFF` 字节。实际文件上限取决于设备和通道的容量。PC 发送开始请求前应检查本地待发送文件长度，再编码为 `uint32`。

`MaxBlockLen` 是 PC 可处理的最大文件块长度，有效范围为 1 至 1400。设备返回 `BlockLenLimit = min(MaxBlockLen, 设备块长上限, 当前链路块长上限)`。PC 确认 `1 <= BlockLenLimit <= MaxBlockLen`、总长度有效，且写入方向的总长度与请求一致后，才使用返回的 `SessionId`，从文件偏移 0 开始传输。

### 顺序读写与完成

1. 双方分别维护已确认的连续字节数。对于**新块**，设备要求 `Offset` 等于当前连续偏移。块长必须满足 `1 <= N <= BlockLenLimit`。先检查 `Offset <= TotalLength`，再检查 `N <= TotalLength - Offset`，避免 `uint32` 加法溢出。末块只传剩余字节。
2. 读取时，设备在应答中回显 `Offset`。PC 核对偏移、实际数据长度和请求的 `Length` 后，将数据写入临时文件。写入时，设备接受完整数据块后返回 `NextOffset`。PC 核对该值等于本块末尾的下一偏移后，才推进本地进度。
3. 连续字节数达到协商的 `TotalLength` 后，PC 发送完成请求。设备核对请求总长度、已连续传输的字节数以及整文件 CRC32。读取方向比对已发送的快照数据，写入方向校验暂存数据并提交。各方向成功的条件见文首流程表。

### 状态码

| Status | 含义 | PC 的处理 |
| --- | --- | --- |
| `0x00` | 成功 | 按当前命令校验成功应答后推进 |
| `0x01` | 读源尚未就绪 | 如需再次检查，以新 RequestId 发送开始请求 |
| `0x02` | 设备暂不可接收写入 | 待设备状态允许后，以新 RequestId 开始 |
| `0x03` | 暂存空间不足 | 报告容量不足，调整后重新开始 |
| `0x04` | 设备忙，已有文件会话或 IAP 活动 | 等待占用解除，以新 RequestId 开始 |
| `0x05` | 参数无效，或通道、方向不支持 | 核对请求参数和通道能力 |
| `0x06` | 会话无效、已过期或命令不适用于当前阶段 | 停止当前操作，核对会话及阶段。会话已失效时须重新开始 |
| `0x07` | 读写的 Offset 与设备连续偏移不符 | 读取附带的 NextOffset 作诊断。只有匹配的成功应答才能确认一块数据，禁止据此跳过未确认字节 |
| `0x08` | 完成时文件长度或 CRC32 不符 | 报告完整性校验失败 |
| `0x09` | 设备读取、写入或提交失败 | 报告当前操作失败 |
| `0x0A` | 当前请求仍在处理 | 等待轮询间隔，使用原 RequestId 查询处理结果 |
| `0x0B` | 仅用于取消应答。设备正在提交，本次取消未执行 | 停止重试取消，按原 RequestId 重发完成请求，查询提交结果 |

### 接收与匹配

1. UDP 先校验对端和数据报边界，串口先完成分帧和 COBS 解码。按功能码分流后，文件接收方检查从站、`11 <= L <= 1415`、实际帧长等于 `L + 7` 和帧 CRC16。从站、长度或 CRC16 校验失败均静默丢弃。
2. 设备只处理标记为 `0xFF` 的请求。若 Command 未在命令布局表中定义，设备静默丢弃，不应答，也不改变会话状态。PC 丢弃请求标记（包括串口回显）。命令体必须符合对应布局，未知状态、命令不匹配或应答长度错误均不能推进 PC 状态。
3. PC 逐项核对**对端、从站、Channel、Command、RequestId**。除开始外，还须核对 SessionId。开始成功时接收设备分配的 SessionId，其余开始应答的 SessionId 忽略。只对当前等待的请求处理一次最终结果。

## 重试与会话结束

PC 实现应避免在重试时意外改变参数或文件数据，例如可保留待确认的发送缓冲区。协议不要求重发帧逐字节一致。设备按本次收到的有效帧处理，无需保存或比对前后两帧的命令体。

| 情形 | 双方行为 |
| --- | --- |
| 请求或应答丢失 | PC 超时后使用原 RequestId 重试。设备按对端、从站、Channel、Command、SessionId、RequestId 识别重试，开始请求忽略 SessionId。首次收到有效请求时使用该帧携带的参数和数据。 |
| 开始应答丢失 | 设备在重试窗口内先识别重复开始，再判断设备忙。重发原会话编号、协商参数或原处理结果，避免重复分配会话和暂存区。 |
| 数据应答丢失 | 若按上述字段匹配到最近一次已接受的读写请求，设备返回该次读取的快照字节或该次写入的 NextOffset。可缓存应答或保存足以重建它的信息。已接受的块只写入一次，CRC 和连续偏移也只累计一次。 |
| 操作仍在处理 | 设备可回复 `0x0A`，操作结束后保存结果，等 PC 使用原 RequestId 再次请求时回复最终应答。 |
| 完成或取消应答丢失 | 即使已释放会话资源，设备仍在重试窗口内保留最终结果。匹配到重试时返回已记录的结果。写入提交已经开始时，重发完成只查询结果。PC 耗尽完成重试仍未获得最终结果时报告**提交结果未知**。 |
| 提交前取消、会话空闲超时或设备复位 | 提交前取消或会话空闲过期时，释放读快照或清理未提交的暂存数据。设备复位或会话过期后，后续传输从新会话的偏移 0 开始。 |
| 提交过程中收到取消 | 对当前会话的取消请求，设备仅应答 `Command = 0x04, Status = 0x0B, L = 11`，回显取消请求的 RequestId。设备照常完成原提交，无需清理数据。此应答是取消请求的最终结果，原完成请求仍可查询。 |

**部署参数**由双方按链路和存储性能确定，包括单次应答超时、轮询间隔、重试次数、结果保留时间和会话空闲期限。结果保留时间须覆盖 PC 的重试窗口。半双工预算应覆盖请求实际发送、收发换向、设备处理、完整应答接收及调度裕量。

## 帧长与联调验收

| 最大块长 N = 1400 时 | 字节数 | 计算 |
| --- | ---: | --- |
| 读成功应答 / 写请求的数据区 L | 1415 | 11 字节公共字段 + 4 字节偏移 + N |
| 原始帧 / UDP 负载 | 1422 | L + 7 |
| 无 IP 选项的 IPv4 包 | 1450 | 1422 + 8 字节 UDP 头 + 20 字节 IPv4 头 |
| 串口单帧线上长度上界 | 1429 | 1422 + floor(1422 / 254) + 2，含末尾分隔符，首次同步分隔符另计 |

在 MTU 为 1500 的以太网上，上述 IPv4 包有 50 字节余量。路径 MTU 较小或 IP 头较长时降低协商块长以避免分片。串口速率、SPI 和缓存也可限制块长。F28335/C28x 实现须将 16 位可寻址单元与线上 8 位字节显式转换。

| 联调场景 | 预期结果 |
| --- | --- |
| 读录波，先未就绪再就绪 | 第一次开始返回 `0x01`，使用新 RequestId 后取得固定快照，收齐并完成校验后发布文件 |
| 写只读通道、运行状态禁止写入、暂存空间不足 | 分别返回 `0x05`、`0x02`、`0x03`，均不能进入写数据阶段 |
| 文件 1401 字节，BlockLenLimit 为 1400，PC 按上限取块 | 两个方向均可传 1400 和 1 字节两块，第二块起点为 1400，全文件 CRC32 只覆盖 1401 字节 |
| 丢弃开始、数据或完成的成功应答后重发 | 各自返回原结果，只建一次会话、只累计一次数据、只提交一次 |
| 首个写请求在途中丢失，同一 RequestId 的重试帧携带不同字节 | 若会话、偏移、块长及帧校验均有效，设备写入实际收到的字节并应答 NextOffset |
| 收到旧会话应答、串口回显、CRC16 损坏帧或帧长不符 | PC 继续等待匹配的应答，文件进度保持原值 |
| 读写偏移跳跃、完成时 FileCrc32 错误 | 前者返回 `0x07` 及连续偏移，后者返回 `0x08`，文件不能报告成功 |
| 提交前取消、空闲过期、设备复位 | 清理快照或未提交数据，过期会话无法继续传输 |
| 提交中发送取消，随后重发原完成请求 | 取消应答为 `0x0B`，暂存数据保留。原完成请求返回处理状态或最终结果，提交只执行一次 |
| 向活动会话发送 CRC16 正确、Command 为 `0x7F` 的请求 | 设备无应答，下一条合法请求仍按原会话进度处理 |
| UDP 共端口、IAP 与文件会话互斥、半双工换向 | 数据交给对应协议，占用时按各协议回复设备忙，半双工每次请求至多收到一条应答 |
| 最大录波和最低支持波特率 | 实测传输时间、应答裕量及设备实时任务表现，据此确定部署参数 |
