# XCP / IAP 传输层约定

## 适用范围

本文规定 UniversalHost 与设备之间通过 UDP 或串口传输 XCP、IAP 数据时的协议区分、帧封装、接收分帧及链路使用规则。串口使用本项目自定义的原始帧封装，并统一采用普通 COBS 编码与 `0x00` 分隔符，支持连续传输，不依赖接收空闲分帧。

本文是本项目串口支持的实现约定。XCP 命令、响应和 DAQ 数据内容沿用现有协议；IAP 的阶段、参数、应答、重试及升级顺序以 [IAP协议.md](IAP协议.md) 为准。

- 字节和长度均指 8 位字节，偏移从 `0` 开始。
- “原始帧”指 COBS 编码前、包含 CRC16 的协议帧；“编码帧”指 COBS 编码结果，不包含分隔符；“线上帧”指编码帧加末尾一个 `0x00`。
- `H` / `L` 分别表示高字节 / 低字节。
- 传输层功能码与 XCP 内容中的 PID / CMD、IAP 阶段码是不同字段。
- CRC16 负责检错，不提供丢包恢复、流量控制或操作去重。

## 链路能力与协议区分

| 传输链路 | XCP | IAP | 协议区分方式 |
| --- | --- | --- | --- |
| UDP | 支持 | 支持 | 使用不同的 UDP 端口 |
| 全双工串口 | 支持 | 支持，与 XCP 互斥 | COBS 解码后的原始帧首字节功能码 |
| 半双工串口，如两线 RS485 | 禁止 | 支持，使用停等收发 | COBS 解码后的原始帧首字节功能码 |

串口原始帧的功能码固定为：

| 功能码 | 协议 |
| --- | --- |
| `0x00` | XCP |
| `0x01` | IAP |

线上首字节是 COBS 块码，不能直接用作功能码。原始帧中的 `0x00` 功能码与线上 `0x00` 分隔符位于不同层次。

XCP 允许设备主动发送 DAQ 数据和异步消息，本项目只在全双工串口上支持 XCP。半双工链路只运行由上位机主导的一请求一响应 IAP。双工能力按实际物理链路判断，不能仅根据串口名称或接口名称推断。

串口 XCP 按点对点链路使用，封装不新增从站地址。IAP 保留原协议中的从站地址及目标设备校验。

## UDP 传输

UDP 沿用现有形式，由配置的 XCP、IAP 端口区分协议，不使用 COBS 或串口分隔符，不添加串口专用的 XCP 功能码和 CRC16。

### XCP on UDP

每个 XCP 传输包的格式为：

```text
| LEN（2 字节，小端） | CTR（2 字节，小端） | XCP 内容（LEN 字节） |
```

- `LEN` 是 XCP 内容的字节数，包含 PID / CMD，不包含 LEN、CTR 本身。
- `CTR` 保持现有 16 位传输计数规则，溢出后回绕；它不是命令应答的请求编号。
- 单包长度为 `LEN + 4`。
- 一个 UDP 数据报允许包含多个完整 XCP 传输包，上位机按各包的 LEN 逐个解析。
- 每个包分别具有 LEN、CTR，不允许将单个包拆到多个 UDP 数据报中。
- 对齐填充如存在，应计入 LEN，不在包尾额外添加未计入长度的字节。
- XCP 内容内部的多字节字段保持原协议规则，不因 LEN、CTR 为小端而统一改变字节序。

### IAP on UDP

直接发送原 IAP 帧，保留 `0x01` 功能码、从站地址、大端长度字段和原 CRC16。上位机继续支持一个 UDP 数据报中包含多条完整 IAP 应答，按每帧的长度字段逐个解析。

UDP 接收端按配置的远端 IP、端口隔离发送端，不将其他设备或其他协议端口的数据交给当前会话。

## 串口帧封装

### XCP 串口原始帧

设 `N` 为 XCP 内容的字节数，即原 XCP on UDP 包中的 LEN。

```text
| 0x00 | 原 XCP on UDP 包（LEN + CTR + XCP 内容） | CRCH | CRCL |
```

| 原始帧字节偏移 | 字节数 | 字段 | 说明 |
| --- | --- | --- | --- |
| `0` | 1 | 功能码 | 固定为 `0x00` |
| `1 .. 2` | 2 | LEN | `N`，小端序 |
| `3 .. 4` | 2 | CTR | 小端序，保持原计数规则 |
| `5 .. 4 + N` | `N` | XCP 内容 | 原 PID / CMD 及后续数据，保持原格式 |
| `5 + N` | 1 | CRCH | CRC16 高字节 |
| `6 + N` | 1 | CRCL | CRC16 低字节 |

原始帧长度为 `N + 7` 字节，且 `N >= 1`。LEN 不包含功能码、LEN、CTR 或末尾 CRC16，也不包含 COBS 编码开销和分隔符。原始帧的 CRC16 之后不得追加填充；表中偏移均指解码后的原始帧，不是线上偏移。

**串口模式下，上位机和设备均必须一帧封装一个 XCP 数据包，禁止合并。** 每个 XCP 包必须独立具有功能码、LEN、CTR 和 CRC16，并独立 COBS 编码、追加分隔符；禁止把多个 LEN / CTR 单元放入同一原始帧，或把多个原始帧合并后共用一次 COBS 编码和一个分隔符。设备不能沿用 UDP 的多包合并封装方式。

该封装适用于所有串口 XCP 消息，包括上位机命令、设备正常或错误响应、DAQ 数据、事件及服务消息。

示例：正常模式 CONNECT 命令的 XCP 内容为 `FF 00`，取 `LEN = 0x0002`、`CTR = 0x0001`：

```text
原 XCP on UDP 包：02 00 01 00 FF 00
CRC16 计算输入：  00 02 00 01 00 FF 00
CRC16 结果：      0xEE5A
完整原始帧：      00 02 00 01 00 FF 00 EE 5A
COBS 编码帧：     01 02 02 02 01 02 FF 03 EE 5A
完整线上帧：      01 02 02 02 01 02 FF 03 EE 5A 00
```

该示例原始帧为 9 字节，编码帧为 10 字节，线上帧为 11 字节。

### IAP 串口原始帧

IAP 原始帧沿用原格式，不再添加额外功能码或额外 CRC16：

```text
| 0x01 | 阶段 | 数据区长度 H | 数据区长度 L | 从站地址 | 数据区 | CRCH | CRCL |
```

设数据区长度为 `L`，原始帧长度为 `L + 7`。长度字段、数据区多字节字段及 CRC16 均保持 IAP 已有的大端序规定。阶段和数据区的具体定义见 [IAP协议.md](IAP协议.md)。

串口发送时，对上述完整 IAP 原始帧（包含原 CRC16）进行一次 COBS 编码，再追加一个 `0x00`。COBS 不改变 IAP 长度字段的含义，接收端解码后交付原完整 IAP 帧。

### 串口 CRC16

XCP 新增的 CRC16 与 IAP 使用完全相同的算法参数及结果发送顺序，实现参考 [Crc.cs](../UniversalHost/Models/Crc.cs) 中的 `Crc.Crc16Modbus.Calculate`。

| 参数 | 规定 |
| --- | --- |
| 算法 | CRC16-MODBUS |
| 位宽 | 16 位 |
| 右移实现的反射多项式 | `0xA001` |
| 对应的非反射多项式 | `0x8005` |
| 初始值 | `0xFFFF` |
| 输入 / 输出反射（RefIn / RefOut） | `true / true` |
| 最终异或值（XorOut） | `0x0000` |
| 计算范围 | 原始帧从功能码开始，覆盖全部帧头及内容，不包含末尾 CRC16 |
| 原始帧结果顺序 | `CRCH CRCL`，高字节在前 |
| ASCII `123456789` 的校验结果 | `0x4B37` |

算法名称中的 MODBUS 不改变本项目的 CRC 字节顺序；本项目规定高字节先发送。

发送顺序为：生成原始帧并计算 CRC16 → 把 CRC16 写入原始帧 → COBS 编码整个原始帧 → 追加 `0x00` 分隔符。接收端先按分隔符取得编码帧，再解码并校验原始帧的 CRC16。COBS 块码和线上分隔符不参与 CRC16 计算；原始帧中的功能码 `0x00` 仍参与计算。

## COBS 编码与连续传输

### 统一线上格式

串口的 XCP、IAP 在两个方向均使用相同的外层格式：

```text
| COBS(一个完整原始帧，包含 CRC16) | 0x00 |
```

编码帧内部只允许出现 `0x01 .. 0xFF`。`0x00` 只作为线上分隔符，每个非空候选编码帧必须独立解码为一个完整原始帧。

```text
COBS(帧1) 00 COBS(帧2) 00 COBS(帧3) 00 ...
```

相邻线上帧可以紧接着发送，无需插入用于分帧的空闲时间。帧内允许因驱动、DMA 或任务调度而分块交付、暂时停顿，接收端保留候选帧直到分隔符到达，不因普通接收空闲而结束候选帧。

新串口会话发送首个线上帧之前，发送端先发送一个单独的 `0x00` 作为同步分隔符。接收端忽略空候选；同步分隔符可结束对方残留的旧候选或异常丢弃状态，不属于任何原始帧，也不参与 CRC16。设备复位后的首次发送按同样规则处理。

连续传输只取消帧边界对时间间隔的依赖，不取消 IAP 的停等流程或半双工链路的方向转换要求。

### 普通 COBS 规则

使用普通 COBS，不使用 COBS/R、COBS/ZPE 或自定义字节编码变体。编码定义参考 [COBS 原论文](https://www.stuartcheshire.org/papers/COBSforToN/)。

- 每个编码块由一个块码和若干非零数据字节组成。
- 块码 `0x01 .. 0xFE` 后跟 `块码 - 1` 个非零字节；解码时复制这些字节，若后面还有编码块，再恢复一个 `0x00`。
- 块码 `0xFF` 后跟 254 个非零字节，解码时复制这些字节，不恢复 `0x00`。
- 最后一块结束后不凭空追加零字节；原始帧末尾的零字节必须通过编码还原，不能被当作线上分隔符删除。
- 本项目发送实现保留最后的结束块；当最后 254 个非零字节恰好形成 `0xFF` 块时，仍输出末尾空块 `0x01`。接收端可接受省略该空块的等价普通 COBS 编码，但必须通过原始帧长度及 CRC16 校验。
- 解码必须检查块码指定的数据是否完整，以及输出是否超限，不能读取候选帧之外的数据。

例如，普通 COBS 编码结果（均不包含线上分隔符）为：

| 原始数据 | 编码结果 |
| --- | --- |
| `00` | `01 01` |
| `11 22` | `03 11 22` |
| `11 00 22` | `02 11 02 22` |
| 254 个 `11` | `FF` + 254 个 `11` + `01` |

以上是编码说明，不是合法 XCP / IAP 原始帧；实际协议帧仍需包含功能码、规定字段及 CRC16。

### 长度与缓存上限

设 `M` 为含 CRC16 的原始帧字节数，按上述发送实现预留：

```text
编码帧容量上限 = M + floor(M / 254) + 1
线上帧长度上限 = M + floor(M / 254) + 2
```

最后一个 `+1` 是线上分隔符。上式是保守上限，实际编码长度随数据内容变化；原始帧不足 254 字节时，线上帧比原始帧增加 2 字节。

设备和 PC 都必须分别规定原始帧、编码候选帧及底层接收缓存的容量上限。容量应覆盖目标设备支持的全部合法 XCP CTO / DTO 和 IAP 帧，不能从未知或损坏的 LEN 字段直接决定无限缓存。

IAP 最大数据帧携带 1372 字节 BIN 数据，原始帧为 1383 字节，编码帧最多 1389 字节，线上帧最多 1390 字节。这是最大情况，设备可以根据自身情况设定IAP每帧携带BIN数据最大字节数。设备的 IAP 接收缓存必须覆盖线上帧长度。

本项目 PC 实现对 XCP 支持 `LEN = 1..65535`，原始帧上限为 65542 字节，编码候选上限为 65801 字节，线上帧上限为 65802 字节；IAP 分别采用 1383、1389、1390 字节上限。底层串口驱动接收缓存设为 256 KiB，每次最多读取 4096 字节。残帧等待预算为当前协议最大线上帧传输时间，加至少 1000 ms 的调度裕量及换向裕量；不使用短接收空闲分帧。

## 串口接收与异常恢复

### 设备与 PC 使用同一分帧流程

双方均将串口视为字节流，持续接收并按 `0x00` 分隔符组帧。一次串口读取、FIFO / DMA 通知允许交付半帧、一帧或多帧，均不能直接当作协议帧边界。

1. 收到非零字节时，追加到当前编码候选帧；收到 `0x00` 时结束候选，空候选直接忽略。
2. 对非空候选进行 COBS 解码。解码失败或输出超限时丢弃该候选，从已经收到的分隔符之后开始下一个候选。
3. 根据原始帧首字节区分协议。XCP 原始帧至少 8 字节，读取偏移 `1 .. 2` 的小端 LEN，要求 `LEN >= 1` 且实际长度等于 `LEN + 7`。IAP 原始帧至少 7 字节，读取偏移 `2 .. 3` 的大端数据区长度，要求实际长度等于 `L + 7`。
4. 执行当前协议的目标设备、长度、CRC16 和字段校验。设备对 IAP 保持原协议“从站地址 → 长度 → CRC16 → 阶段 / 数据区”的判定顺序及错误应答规则；XCP 长度或 CRC16 错误时丢弃，不执行命令。
5. 只有有效原始帧才能触发业务操作或被上位机作为有效响应接受。XCP 去除功能码和末尾 CRC16 后交付原 LEN / CTR / XCP 内容；IAP 使用原完整 IAP 帧进行协议分析。
6. 继续处理当前读取块中的后续字节，保留尚未遇到分隔符的编码候选。

原始帧的 LEN 用于解码后的完整性校验，不用于决定线上帧边界。不在无效候选内部逐字节搜索功能码，也不把一个候选拆成多个原始帧。

PC 一次读取或一次写入多条分别封装的完整线上帧属于字节流批量处理，不违反“一帧一个 XCP 包”的规定。

### 错误与重新同步

- COBS 解码失败、未知功能码或无法确认的候选不得触发业务操作；无法安全构造协议错误应答时静默丢弃。能够完整解码的 IAP 候选按原 IAP 校验及错误应答规则处理。
- 已收到分隔符的坏帧丢弃后，直接开始收集下一候选；不额外等待或跳过另一个分隔符。
- 尚未收到分隔符时，若编码候选超限、底层接收溢出或残帧等待超时，清空候选并进入“丢弃至下一个 `0x00`”状态；消费该分隔符后再收集新帧，不能把残帧尾部作为新帧起点。
- 分隔符被插入、丢失或损坏时，可能导致当前帧或相邻帧丢弃；后续完整分隔符提供重新同步边界。CRC16 继续负责检错，不保证损坏数据一定能被检测，也不补偿已经丢失的帧。
- 残帧超时只用于异常清理，不用于正常分帧。其预算必须覆盖最长合法帧的传输及允许的驱动、任务调度延迟，不设置成 UART 短空闲阈值。

### 设备持续接收要求

设备必须在没有 UART IDLE 事件的连续数据流中仍能及时处理接收数据。可根据平台能力使用循环 DMA、DMA 半满 / 满通知、FIFO 批量中断或定期读取；IDLE 可作为处理新增字节的辅助通知，但不能作为协议帧边界或唯一处理触发条件。

编解码及 CRC16 可在低优先级通信任务中分批处理，使用固定缓存并控制处理时间。允许边解码边计算 CRC16，但 CRC16 和协议校验通过前不能执行命令、写入 Flash 或接受升级进度。

C2000 C28x 实现必须区分 16 位可寻址存储单元与本协议的 8 位字节。输入、输出字节值限定为 `0..255`，COBS 块长仍以 8 位字节计数，不能使用平台 `sizeof` 结果直接代替线上字节数；可以采用每个 16 位元素存一个字节，或通过平台字节访问机制紧凑存储。

## 串口模式下 XCP / IAP 互斥

**上位机必须先关闭 XCP 设备连接，才能进入 IAP；IAP 进行期间禁止连接设备开启 XCP。** 该规则适用于全双工串口上的协议切换，半双工串口始终禁止 XCP。

| 上位机串口状态 | 允许连接 XCP | 允许开始 IAP |
| --- | --- | --- |
| 未连接且无 IAP 会话 | 全双工时允许 | 允许 |
| XCP 正在连接、已连接或正在断开 | 不允许重复连接 | 禁止 |
| IAP 正在准备、执行、取消或清理资源 | 禁止 | 不允许重复开始 |

- “关闭 XCP 连接”必须包含停止 DAQ、心跳及其他 XCP 收发，结束相关任务并释放串口占用。仅停止监控或修改界面连接标志不满足进入 IAP 的条件。
- XCP 连接未关闭时，上位机拒绝开始 IAP，并提示用户先断开设备连接。
- 从 IAP 开始准备直到会话结束并完成资源清理，上位机必须持续禁止所有 XCP 连接入口，包括菜单、快捷键和其他调用入口。
- 互斥必须由业务层统一检查，避免连接 XCP 与开始 IAP 同时触发时都通过检查；不能仅靠按钮禁用保证。
- 每个串口同一时刻只由一个会话持有，一个接收流程消费输入，一个发送流程按完整帧顺序输出；禁止多个读取者争抢数据或多个写入者交错发送字节。
- 会话切换时处理旧接收缓存和残留数据，旧 XCP 数据不能成为 IAP 应答，旧 IAP 应答不能成为新 XCP 连接的响应。
- IAP 成功、失败或取消后，完成资源清理才解除互斥，不自动恢复 XCP 连接。IAP 失败或取消不等于设备已经返回 APP。

此互斥规定仅针对串口模式，不改变 UDP 按不同端口使用两种协议的现有方式。

## 半双工 IAP 收发

- 上位机发送请求，设备接收并处理，设备完成后回复，上位机收到匹配的成功 ACK 后再发送下一帧或下一条命令。
- 超时重试、耗时操作的重复请求及结果保存遵循 [IAP协议.md](IAP协议.md)，传输层不得改变阶段顺序或重复触发擦写、重启。
- 请求或应答的整个线上帧（含末尾 `0x00`）必须实际发送完毕后才切换收发方向，并为收发器及适配器的方向转换留出时间。驱动写入完成不一定表示线上发送完成。
- 双方不得主动发送与当前 IAP 流程无关的数据；半双工链路不得运行 XCP DAQ、心跳或其他 XCP 消息。
- 对存在发送回显的适配器，上位机必须处理本机回显，不能把自身请求作为设备应答。

## 上位机超时与采样率

超时设置、发送队列调度由上位机负责，必须按当前串口带宽、COBS 后的线上长度及设备时序调整，不能直接照搬 UDP 参数。全双工连续发送无需为分帧安排帧间空闲。

### 超时预算

设波特率为 `baud`，每个字符的线上位数为 `bits_per_char`，COBS 编码并添加分隔符后的帧长度为 `wire_bytes`：

```text
bits_per_char = 1 个起始位 + 数据位数 + 校验位数 + 停止位数
frame_time    = wire_bytes * bits_per_char / baud
```

8N1 对应 `bits_per_char = 10`。一次请求到收到完整应答的时间预算应覆盖：发送排队及编码、请求实际发送、设备解码及处理、半双工方向转换（如适用）、应答编码及实际发送、适配器传输、PC 解码及调度裕量。超时计时起点必须明确，尚未实际发送的排队时间不能被误认为设备响应超时。

例如，`115200、8N1` 下，IAP 最大数据帧的原始长度为 `1383` 字节，线上长度最多 `1390` 字节，单是请求发送就最多约需 `121 ms`。新会话首次发送的同步分隔符需额外计入一次。

残帧等待超时、命令应答超时及 IAP 阶段总超时是不同概念，应分别处理。IAP 阶段重试规则仍以 IAP 协议为准；上位机应保证前一帧已经实际发送完毕，不因低波特率而不断排队重试帧。

### DAQ 带宽预算

```text
单方向理论字节率 = baud / bits_per_char
单个 XCP 原始帧字节数 M = LEN + 7
单个 XCP 线上帧字节数 = COBS 编码帧字节数 + 1
单个 XCP 线上帧长度上限 = M + floor(M / 254) + 2
DAQ 所需字节率 = 每秒采样事件数 * 每次事件全部线上帧的字节数之和
```

`115200、8N1` 的单方向理论上限为 `11520 字节/秒`。每次采样如只有一个 `LEN = 32` 的 XCP 包，则原始帧为 `39` 字节，线上帧为 `41` 字节，仅按线上字节数估算约为 `281 帧/秒`；这只是未计其他流量和处理开销的理论上限。

设备配置采样率时还必须考虑一次采样产生的全部 ODT 帧、响应和异步消息、编解码与 CRC16 耗时、发送排队及接收处理能力，并预留带宽裕量。对随数据变化的编码长度，应按上限估算容量和最高采样率。全双工两条方向分别计算带宽，不能把两方向容量相加后用于设备到 PC 的 DAQ 数据。

## 丢帧与异常处理

- 串口 XCP 的 COBS、长度或 CRC16 错误帧不交给 XCP 处理，不新增传输层错误应答或自动重传机制。
- DAQ 坏帧丢弃，CTR 缺口及接收队列丢帧按原诊断规则统计，不通过重传补齐实时采样。
- XCP 命令未收到有效响应时按命令超时处理。有副作用的命令不得由串口传输层盲目重发；恢复或重新同步由 XCP 会话流程处理。
- IAP 继续检查从站、阶段、数据帧号及结果码，按原协议重试和处理重复请求，不能因 CRC16 正确就把不匹配的响应当作当前请求成功。
- 串口断开、取消或接收异常后，上位机必须结束当前收发并释放资源，完成清理后才允许开始新的串口会话。
